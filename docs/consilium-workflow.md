# Проверка обязательного цикла консилиума

Профиль v1 — локальная CLI-проверка. Он не изменяет MCP, старый team_work, fresh-место, полномочия Claude или серверный доступ. Для принятия старым gate по-прежнему нужны все его условия. Прямые вызовы инструментов и текст ответа в чат CLI не блокирует.

Обязательная последовательность: независимое обсуждение исходного запроса; план по обсуждению; последовательные этапы с коллективной оценкой каждого; общий итоговый аудит исходного запроса и исправления; показ пользователю. Текущий кворум — Codex, Grok, Antigravity. Недоступный Claude не заменяется подписью другого участника.

```text
node tools/consilium/workflow.js snapshot --file WORK/workflow.json --stage pilot
node tools/consilium/workflow.js check --file WORK/workflow.json --stage pilot --intent start
node tools/consilium/workflow.js check --file WORK/workflow.json --stage pilot --intent accept
node tools/consilium/workflow.js check --file WORK/workflow.json --intent deliver
```

`snapshot` только вычисляет пакет для нового ревью, возвращает `ready:false`, не принимает текущий или предшествующие этапы. `start` проверяет принятых предшественников, не требует ещё не созданных выходных файлов текущего этапа и не означает его принятия. `accept` и `deliver` перечитывают материалы и действующие отзывы. Код 0 относится только к выбранному действию. Отказ проверки — 2; ошибка схемы/чтения — 3. Никаких shell-команд из JSON не исполняется.

Корень работы — каталог workflow.json. Запрос задаётся `{path,sha256}`. Требования — `{id,quote,evidence_needed}`; quote должна дословно входить в запрос. Текст запроса не заменяется пересказом плана.

Реестр имеет структуру:

```json
{
  "schema_version": 1,
  "work_id": "night3-comparison",
  "quorum": ["codex", "grok", "antigravity"],
  "request": {"path": "request.txt", "sha256": "SHA256"},
  "requirements": [{"id": "R1", "quote": "Дословная часть запроса", "evidence_needed": "Что проверять"}],
  "stages": [
    {"id": "discussion", "kind": "discussion", "depends_on": [], "addresses": ["R1"], "criteria": ["Проверен исходный запрос"], "material": [{"path": "discussion.md"}], "reviews": []},
    {"id": "plan", "kind": "plan", "depends_on": ["discussion"], "addresses": ["R1"], "criteria": ["Оперативный P2-план вытекает из обсуждения и исторических P0/P1"], "material": [{"path": "P2-plan.md"}, {"path": "history/P0-discussion.md"}, {"path": "history/P0-plan.md"}, {"path": "history/P1-results.md"}], "reviews": []},
    {"id": "pilot", "kind": "execution", "depends_on": ["plan"], "addresses": ["R1"], "criteria": ["Пилот соответствует плану"], "material": [{"path": "pilot-manifest.json"}], "reviews": []},
    {"id": "rest", "kind": "execution", "depends_on": ["pilot"], "addresses": ["R1"], "criteria": ["Остальная серия оценена по принятому пилоту"], "material": [{"path": "rest-manifest.json"}], "reviews": []},
    {"id": "final", "kind": "final", "depends_on": ["rest"], "addresses": ["R1"], "criteria": ["Исходный запрос выполнен"], "material": [{"path": "gallery.html"}], "reviews": [], "coverage": [{"requirement_id": "R1", "result": "met", "evidence_refs": ["gallery.html"], "limitations": ""}]}
  ]
}
```

SHA256 в примере — место для вычисленного значения. После snapshot записывают `snapshot_sha256` в этап; для execution/final ещё `accepted_plan_sha256`, равный снимку plan. План хеширует объявленную последовательность и критерии всех этапов. Каждый следующий снимок включает хеш предыдущего и хеш плана. Изменение плана или файлов делает голоса устаревшими. Исторические отзывы не получают новые SHA задним числом: их можно включить как материал нового свежего ревью.

Все фактические изображения, промпты, таблицы и галерея, на которые опирается итог, должны входить в material напрямую. Ссылка в HTML или манифесте не включает связанный файл автоматически. Набор material и полноту требования проверяют трое; SHA не доказывает качество или полноту. Каждый этап имеет непустые criteria, material и addresses. Исполнительных этапов может быть несколько, но цепь последовательная. Обсуждение фиксирует позиции и может содержать несогласие; план и каждый следующий этап требуют трёх ПРИНЯТО.

## Голоса моста

Отправляйте настоящее поручение с ролью «проверка», новым сеансом Codex без записи и самостоятельными строками:

```text
workflow_work: night3-comparison
workflow_stage: pilot
snapshot_sha256: <полный хеш снимка>
```

Ответ сам должен содержать ровно одну строку `snapshot_sha256: <тот же хеш>`. Последняя непустая строка — ровно `ПРИНЯТО` или `НЕ ПРИНЯТО: N блокирующих`. Конечные пустые строки/пробелы разрешены; произвольный текст или Markdown после вердикта не удаляются. Служебный конверт Grok снимается только существующим parseReply после проверки сохранённой доставки team-store.source. HMAC доставки не доказывает конкретную image-модель.

В reviews — ровно по одному объекту для каждого участника:

```json
{"participant":"grok","source":"bridge","job_id":"РЕАЛЬНЫЙ_ID","task_sha256":"SHA256","response_sha256":"SHA256"}
```

Хеш поручения берётся по `taskText(job)` из общего модуля, хеш ответа — по полным сохранённым байтам (для Grok вместе со служебным конвертом). Источник состояния — штатные team-store.list/source; это чтение, не запуск серверов. Адаптер смотрит все наблюдаемые ревью по work/stage/snapshot, включая незавершённые, отменяемые и поздние. Порядок определяется последним известным событием карточки: startedAt/createdAt/created_at, finishedAt, cancel_requested.at, late_result.receivedAt. Для done время finishedAt обязательно. Новый нерешённый запрос, stop_unconfirmed или поздняя доставка блокируют возврат к старому ПРИНЯТО; нужен более новый действующий завершённый ответ. Неизвестные времена или неоднозначный одинаковый порядок дают отказ. Отменённые/поздние ответы сами голосами не становятся; requested/reported mismatch и неизвестные источники не принимаются. Конкретная модель указывается только на уровне доказательства provenance.

## Ограниченная политика импорта нативного Codex — предложение для ревью кандидата

По умолчанию импорт запрещён. В этой работе нужна возможность сохранить настоящий ответ нативного Codex-помощника с ID и полной записью tool-result. Это локальная регистрация на доверии к оркестратору, не аутентифицированный мост. Файл с текстовым SHA не доказывает автора, время или отсутствие более позднего отказа. Политика должна быть явно согласована всеми тремя и закреплена в workflow.import_policy как `{path,sha256}`. Публичный результат сохраняет предупреждение о границе доверия.

Политика JSON: `schema_version:1`, постоянный `policy_id`, `mode:"recorded_response_not_independently_authenticated"`, `scope:"native_codex_only"`, `enabled:true`, `trust_boundary` с явным описанием ограничений. `agreement` содержит три записи `{participant,job_id,source_record,response:{path,sha256}}` — полные сохранённые ответы по точной политике. Их последняя строка ПРИНЯТО, а самостоятельные строки `import_policy_id` и `import_policy_sha256` связывают редакцию. Второй хеш — SHA-256 канонического JSON перечисленных шести полей политики без agreement; `canonical()` экспортируется модулем. Это устраняет самоссылку, не превращает локальные копии соглашения в аутентифицированные голоса. Подлинные источники соглашения проверяются при ревью кандидата/применения политики; валидатор подтверждает только их сохранённые байты и явное заявление.

Запись импортированного голоса: `participant:"codex"`, `source:"native_codex_import"`, реальные `job_id`, `agent_id`, `thread_id`, `source_record`, `finishedAt`, поручение `task:{path,sha256}`, полный ответ `response:{path,sha256}`. Поручение содержит work/stage/snapshot; собственная строка snapshot в ответе обязательна. Нет строки — новое ревью, а не дописывание в старый ответ. Grok/Antigravity этим маршрутом импортировать нельзя. Выборка всей истории импортированных ответов машинно не подтверждается: оркестратор обязан сохранять отрицательные ответы и направлять последнюю редакцию всем троим.

Наличие документа с предложением политики ещё не означает, что она согласована или включена. Без явного policy-файла и трёх записей соглашения CLI отклоняет импорт.

## Файлы и ресурсные границы

Допускаются обычные файлы и ссылки, чей окончательный realpath остаётся внутри корня работы. Выход наружу запрещён; повтор одного resolved-файла в material этапа отвергается. При чтении сверяются размер, inode, mtime, ctime и разрешённый путь. Лимиты: JSON 8 MiB, один текст 16 MiB, 4096 ссылок, файл 512 MiB, сумма уникальных файлов 32 GiB. Хеширование потоком блоками до 1 MiB. Нельзя считать эти пределы параметрами качества изображений. Файлы/журналы под контролем локального пользователя не защищены от намеренной согласованной переписи; это не доверенное хранилище.

Перед упаковкой готового результата скрипт обязан вызвать `check ... --intent deliver` и проверить код возврата. Черновики можно собирать с явным статусом «не принято». Эта интеграция ограничивает конкретную упаковку; глобального запрета обхода генераторов/чата не появляется.

Проверки: `node tests/run.js consilium-workflow.js`; набор также включён в обычный полный `node tests/run.js`. Прямой `node tests/consilium-workflow.js` допустим для отладки. Изолированные тестовые данные сохраняются во временной папке; тест не удаляет файлы и не пишет в рабочие журналы моста.
