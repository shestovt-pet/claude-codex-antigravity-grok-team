# trio-v4: исправления по ревью c9b0fd37

Основание: независимое ревью кандидата `645c585c62db39bbba3ef782b53dc6f463622ce4` и улучшение Antigravity mujifsyv. Рабочая копия: `C:\most\.work\trio-v4`.

## Результат

1. **Перенос после перезапуска.** Вызов переноса удалён из deploy. Четыре основных сервера вызывают общий запуск переноса до подключения MCP, записи готовности и запуска очередей. Общая межпроцессная блокировка служит барьером. Промежуточный запуск со старым хранилищем, гости и пробные запуски переноса не выполняют.
2. **Догоняющая сверка.** Метка готовности больше не завершает обработку досрочно. Источники сверяются при каждом запуске и затем каждые 300 000 мс, пока хотя бы один прежний источник существует. Один процесс не запускает наложенные фоновые проходы, проходы разных процессов разделены общей блокировкой. Таймер не удерживает завершающийся процесс. Новые номера дозабираются.
3. **Приоритет окончательного состояния.** Окончательными считаются `done`, `applied`, `failed`, `cancelled`. Они могут заменить незавершённый комплект, включая карточку, которую новый сервер уже отметил как потерянную. Обратного перехода из окончательного состояния по старой незавершённой копии нет. Обновление выполняется под штатной блокировкой задания: сначала файлы, затем атомарная запись карточки. Повторный проход распознаёт уже перенесённый снимок и не публикует его повторно. Занятая карточка остаётся следующему проходу.
4. **Конфликт и гонки чтения.** Разные окончательные комплекты сохраняются в карантине обоими снимками; действующая карточка получает конфликт, принятие голоса запрещено. Первоначальные источники сохраняются. Карточка читается до списка файлов и повторно сверяется: её изменение во время чтения откладывает перенос, а не создаёт ложный карантин. Прерывание до публикации не мешает следующей сверке, даже если метка готовности уже существует.
5. **Диагностика.** `team_status` показывает ошибки журнала переноса с номерами заданий, карточки карантина с причинами и ошибку последнего неудачного фонового прохода. После успешного прохода отдельная ошибка фоновой сверки отмечается как разрешённая. Счётчики перенесённых и обновлённых комплектов накапливаются; сведения об ошибках и конфликтах сохраняются без одинаковых повторов. Карточки состояния team переносятся первоначально: периодическая сверка заданий не откатывает новые голоса и снимки квоты.
6. **Правила.** В `rules/brief.md` восстановлен общий порядок `merge → deploy` с перезапуском. Разовый двухшаговый переход с d99824c изложен в README и `rules/claude.md`; перенос там происходит при запуске новых серверов после второго перезапуска.

Пять пропусков: три проверки удаления/очистки отключены по запрету удалений; одна проверка дерева процессов недоступна из-за запрета `taskkill /T`; одна проверка файловой символической ссылки недоступна на Windows. Проверки переходов каталогов выполнены.

Живая установка, пользовательские настройки и настоящий Claude Desktop не переключались. В проверках запуск сценария перезапуска заменяется подтверждающим тестовым обработчиком; сами MCP-серверы запускаются настоящими процессами. Периодический проход проверен управляемым планировщиком с проверкой интервала 300 000 мс, без ожидания пяти минут. Эти ограничения проверки не меняют реализованный порядок.

Коммит не создан, `.git` рабочей копии использовался только для чтения. Исходные файлы не удалялись и не переименовывались. После ревью Claude или сервер team должен зафиксировать перечисленные файлы. Обязательных удалений или переименований для исправления нет. Временные каталоги проверок `tests/.tmp-*` и `most-part2-*` оставлены; при необходимости их отдельно очищает Claude после сверки журнала и завершения процессов. Очистка тестами отключена через `MOST_TEST_KEEP=1`.
