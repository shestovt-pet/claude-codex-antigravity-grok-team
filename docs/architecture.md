# Связка Claude, Codex, Antigravity и Grok — 0.4.0

Claude организует работу и принимает результаты. Codex пишет и проверяет код. Antigravity анализирует тексты и замысел. Четыре локальных сервера предоставляют инструменты Claude Desktop. Grok — пробный критик и автор, его голос совещательный. Серверы работают, пока открыто приложение; история чата автоматически в отдельные поручения не передаётся.

## Серверы и инструменты

| Сервер | Инструменты |
| --- | --- |
| `antigravity` | `antigravity_status`, `antigravity_send`, `antigravity_result`, `antigravity_apply`, `antigravity_cancel` |
| `codex` | `codex_status`, `codex_send`, `codex_result`, `codex_cancel` |
| `grok` | `grok_status`, `grok_send`, `grok_result`, `grok_cancel` |
| `team` | `team_status`, `team_rules`, `team_work`, `team_change` |

Antigravity получает поручение и материалы; перенос проверенного результата выполняется отдельным вызовом `antigravity_apply`. Запрет записи для самого Antigravity передаётся в поручении: техническую песочницу для него мост не создаёт. Codex по умолчанию работает только на чтение; `write=true` разрешает изменения в указанной папке. После сбоя задания с записью решение о продолжении принимает Claude.

`team_rules(part=common|claude|antigravity|grok|all)` читает правила из зафиксированного коммита `main`. `team_status` показывает квоты, работы, карточки поручений, версии и состояние конфигов. Снимок Claude передаётся как `claude_quota: {percent, source, taken_at, resets_at?}`; процент означает использованную долю. Отсутствие данных показывается явно.

`team_work` принимает `create|update|get|list|claim`, `name`, `expected_revision` (для `list` имя не нужно). Для создания редакция — 0, далее — последнее прочитанное число. Для новой работы обязателен `owner` — метка сеанса; она передаётся при дальнейших действиях. `status_sent=true` отмечает уже отправленный пользователю статус. `claim` передаёт владение после часа без активности и живых поручений с проверкой `expected_revision`. Поля: `goal`, `done_criteria`, `stages`, `next_step`, `reminders`. Этап: `{title, weight, accept_criteria, state, evidence?, version?}`; состояния — `план`, `идёт`, `принят`; веса в сумме 100. Для принятия обязательны доказательство и версия. Изменение плана либо пересмотр принятого требует `plan_change`; пояснения сохраняются в `plan_changes`. Напоминания создаёт Claude, сервер хранит до трёх их идентификаторов.

## Где что лежит

- `servers/<имя>/index.js` — точки запуска; `common/` — общая логика.
- `rules/`, `AGENTS.md`, `lessons.md`, `skill/helpers/SKILL.md` — правила и накопленный опыт.
- `docs/design/` — замысел и ТЗ; `docs/part2-report.md` — отчёт реализации.
- `.work/<имя>/` — самостоятельные клоны изменений с `origin=../..`, ветка `change/<имя>`.
- `works/<имя>.json` — состояние работы и редакция; `works/status.md` — производное представление. Они исключены из Git, чтобы текущие работы не мешали слиянию кода.
- `live/<полный-хеш>/` — отдельные релизы; `live/deployed.json` — отметка последнего развёртывания. После отката актуальные пути следует смотреть в конфигах.
- `C:\most\state\jobs` — задания Antigravity; `codex-jobs` — Codex; `grok-jobs` — Grok; `team` — вердикты и снимок Claude; `locks` — сведения о блокировках. `%LOCALAPPDATA%\most` и `live\.deploy-state` — источники переноса прежних заданий. Старые задания Codex читаются как архив из прежней папки переходника.

Основные настройки среды: `MOST_REPO_ROOT`, `MOST_STATE_DIR`, `MOST_CODEX_JOBS_DIR`, `MOST_CODEX_ARCHIVE_DIR`, `MOST_CODEX_SESSIONS`, `CODEX_PATH`, `AGY_PATH`. `MOST_CLAUDE_CONFIGS` — массив абсолютных путей конфигов в JSON. В релизах конфиги явно задают `MOST_REPO_ROOT`, чтобы работы и правила оставались в основном репозитории.

## Изменения и развёртывание

Нужны Node.js ≥18, Git и `tar` в PATH, npm рядом с Node.js. Зависимости — MCP SDK и zod из `package-lock.json`.

Обычный порядок через `team_change`:

1. `start(name)` создаёт клон. Имя: 1–40 строчных латинских букв, цифр и дефисов.
2. После правок `commit(name, message)` фиксирует кандидата и аннулирует прежние голоса. `diff(name, from_char=0)` показывает изменения порциями до 24 000 символов, включая незакоммиченные изменения.
3. Claude передаёт обоим проверяющим точные хеши `base` и `candidate`. Codex проверяет новым сеансом на чтение, Antigravity — в режиме `review`.
4. `verdict(name, who, base, candidate, decision, job_id?)` записывает голос. Для помощников нужны завершённое задание, оба хеша в поручении и последняя строка результата `ПРИНЯТО`. Решение пользователя задаётся `who=user`, `decision=РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ`, `replaces=<один участник>`, `quote=<точные слова>`.
5. `merge(name)` требует чистого клона кандидата, отсутствия изменений отслеживаемых файлов и индекса в корне, прежней базы `main` и принятия Codex, Antigravity и Claude, а также учёта совещательного ответа Grok; выполняет fetch из клона и только `--ff-only`. Неотслеживаемые файлы в корне сами по себе не мешают; если слияние затронет такой файл, Git откажет без его перезаписи.
6. `deploy(commit=main)` извлекает коммит через `git archive`, устанавливает зависимости, проверяет запуск серверов и переключает конфиги. `rollback` возвращает серверные записи из `.prev`, сохраняя посторонние поля.

Первоначальная установка, когда team ещё не подключён (приёмку коммита обеспечивает Claude):

```powershell
node C:\most\.work\team-v1\tools\deploy.js --root C:\most --commit <хеш> --release-only --dry-run
node C:\most\.work\team-v1\tools\deploy.js --root C:\most --commit <хеш> --release-only
```

Явные пути конфигов можно передать повторением параметра:

```powershell
node C:\most\.work\team-v1\tools\deploy.js --root C:\most --commit <хеш> --config "C:\путь\первый.json" --config "C:\путь\второй.json"
node C:\most\.work\team-v1\tools\deploy.js --root C:\most --rollback
```

По умолчанию обрабатываются только существующие конфиги `%APPDATA%\Claude\claude_desktop_config.json` и `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json`. Меняются записи четырёх серверов; удаляются `most` и старые записи с `mcp-server-google-antigravity` в аргументах. Остальные поля и серверы сохраняются. На Windows команда — `C:\Program Files\nodejs\node.exe`, если он существует; иначе `node`.

Установка использует `npm ci --omit=dev --ignore-scripts`. Пробный запуск выполняет MCP initialize и tools/list в отдельном хранилище; очереди поручений при нём отключены. Готовый каталог релиза публикуется одним переименованием. Код существующего релиза не перезаписывается; при переходе с d99824c после повторной проверки обновляется только метка `probe-ok.json`. Повторное переключение на тот же релиз не заменяет `.prev`. Перед заменой конфигов проверяются время изменения и содержимое. При сбое выполняется компенсация; если чужая правка мешает восстановлению, ответ явно сообщает о частичном обновлении.

**Перезапуск Claude — при каждом обновлении серверного кода** (`restart_claude=true` делает его сам). Правила читаются из `main` без перезапуска. Развёртывание не удаляет старые релизы и диагностические временные каталоги; очистку выполняет Claude отдельно.

### Первоначальная установка по частям

Если запись разрешена только в текущую папку, Claude организует отдельные запуски Codex. Команды запускают скрипт принятого кандидата `C:\most\.work\team-v1\tools\deploy.js`: до слияния файла `C:\most\tools\deploy.js` нет. После сборки можно запускать скрипт из релиза `C:\most\live\<хеш>\tools\deploy.js`. `<хеш>` заменяется полным хешем принятого коммита.

Сначала запуск с рабочей папкой `C:\most\live`:

```powershell
node C:\most\.work\team-v1\tools\deploy.js --root C:\most --commit <хеш> --release-only --node-modules-from C:\most\node_modules
```

`--release-only` создаёт релиз, проверяет все четыре сервера и записывает в релиз `probe-ok.json`. Конфиги не читает и не меняет. Архив и подготовленный каталог остаются в `live`; блокировки, данные пробного запуска и кэш npm — в `live\.deploy-state` (можно задать другую разрешённую папку через `--state-dir`). Параметр `--node-modules-from` копирует указанную папку зависимостей вместо обращения к npm; нужны готовые зависимости для той же системы, без ссылок и переходов каталогов. Без параметра используется `npm ci`.

Затем отдельный запуск с рабочей папкой каждого конфига:

```powershell
node C:\most\.work\team-v1\tools\deploy.js --config-only --release C:\most\live\<хеш> --config .\claude_desktop_config.json
```

`--config-only` требует явные `--release` и `--config`, проверяет метку пробного запуска и наличие четырёх серверов. Только читает релиз; сохраняет прочие поля конфига и создаёт `.prev`. Блокировки располагаются в `.deploy-state` рядом с конфигом (либо в `--state-dir`). Повторный запуск на тот же релиз сохраняет прежнюю резервную копию. `--dry-run` доступен в обоих режимах без записи. Отметка `live/deployed.json` при раздельной установке не обновляется: актуальные пути видны в конфигах и `team_status`.

При первом переходе старый `C:\most\index.js` сохраняется до живой проверки. Claude доставляет принятый коммит кандидата в Git основного репозитория через fetch, собирает его через `--release-only --commit <хеш>` до слияния, переключает конфиги, затем пользователь перезапускает Claude. До слияния проверяются запуск серверов, наличие и работа инструментов, квоты и перенос результата. Только после этих проверок Claude перематывает `main` через `ff-only` на тот же коммит. После `ff-only` проверяются `team_rules` из новой `main` и проектный `AGENTS.md`. После этого перехода откат на 0.2.0 через `.prev` невозможен: прежнего `C:\most\index.js` больше нет, и проверка отката откажет. Для `--release-only` принадлежность коммита ветке `main` не требуется; обычный `team_change deploy` по-прежнему требует её.

Откат одного конфига из его папки: `node C:\most\.work\team-v1\tools\deploy.js --config-only --rollback --config .\claude_desktop_config.json`. Релиз указывать не нужно. Перед записью проверяются локальные пути прежних серверов из `.prev`. Если прежний сервер исчез, этот конфиг остаётся без изменений, а ответ объясняет причину; остальные конфиги обрабатываются независимо.

Отрицательный вердикт помощника также можно записать через `team_change verdict` с `decision=НЕ ПРИНЯТО`: последняя строка его задания должна иметь вид `НЕ ПРИНЯТО: N блокирующих` (N больше нуля). Такой голос сохраняется в карточке изменения и блокирует слияние до нового принятия.

## Что делать пользователю

Ничего. При переходе с d99824c Claude выполняет два вызова одного принятого коммита, как описано ниже. При последующих обновлениях после слияния Claude вызывает `team_change deploy` с `restart_claude=true`: сервер сам закрывает и снова открывает Claude Desktop (скрипт запускается вне Claude и ждёт готовности всех четырёх серверов нового релиза), итог показывает уведомлением Windows и пишет в `C:\most\live\restart\<номер>.log`. Проверка версии — `team_status` (пути серверов в Claude, Codex и Antigravity ведут в один релиз).

## Общий сервер в трёх приложениях

`deploy` подключает серверы не только к Claude: в `%USERPROFILE%\.codex\config.toml` (блок между строками `# most:begin` и `# most:end`) — team, antigravity и grok; в `%USERPROFILE%\.gemini\config\mcp_config.json` — team, codex и grok, и добавляет разрешения `mcp(team/…)`, `mcp(codex/…)`, `mcp(grok/…)` в `%USERPROFILE%\.gemini\config\config.json`. Себя никто не получает. В чужих приложениях серверы работают гостями (`MOST_CLIENT`): чтение состояния и постановка поручений в очередь; исполняет основной сервер в Claude Desktop. Для всех файлов создаётся `.prev`, `rollback` возвращает их.

## Ворота запроса и замысла

`team_change start` требует `request` (дословный запрос пользователя) и `design_file`; печатает метку запроса «#xxxxxxxx» и хеш замысла. `team_change design(name, who, job_id, decision)` записывает голос помощника по замыслу; без «ПРИНЯТО» Codex и Antigravity `commit` откажет. `diff` первым блоком печатает запрос; `verdict` помощника требует метку запроса в поручении. Замечание «[системное]» требует перед `merge` урока в lessons.md и правки инструментария либо вердикта Claude «системное — открыто в уроке N».


Полный прогон сохраняет вывод в `tests/windows-test-output-part2.txt`. Тесты используют поддельные исполнители, отдельные хранилища и временные репозитории; сеть и рабочие конфиги не используются. ## Изменения trio-v4

Старые хранилища переносятся целыми комплектами под общим замком; очереди ждут завершения. При расхождении сохраняются оба комплекта, состояние — «ПЕРЕНОС: КОНФЛИКТ». Код не выбирает результат за дирижёра. Коммит помнит хеш замысла; слияние после изменения замысла требует нового кандидата и новых голосов.

Grok читает адрес и ключ из state/grok-webhook.json, отправляет поручение один раз и проверяет HMAC-SHA256 ответа. Брифы — state/grok/briefs, ответы — state/grok/replies, закрытые карточки и ключи — state/grok-jobs. После приёма, потери или отмены ключ затирается. Поздние ответы после этого — только данные. Настройки приложения и разрешения пользователя код не меняет. Подробнее: rules/grok.md.

Проверки Windows и ограничения: docs/trio-v4-report.md; полный вывод: tests/windows-test-output-trio-v4.txt.

### Переход с d99824c без участия пользователя

После приёмки и слияния Claude вызывает старый `team_change deploy(commit=<полный хеш кандидата>, restart_claude=true)`. Старый сервер собирает релиз и переключает три сервера на новый код, сохраняя `MOST_STATE_DIR=C:\most\live\.deploy-state`. Новый код поддерживает этот промежуточный режим.

После возврата инструментов Claude повторяет `team_change deploy` с тем же полным хешем и `restart_claude=true`. Новый сервер перепроверяет четыре сервера и гостевые подключения, обновляет метку `probe-ok.json` старого формата, переключает Claude, Codex и Antigravity на общее хранилище и подключает Grok. После второго перезапуска новые серверы переносят задания в `C:\most\state` под общим барьером до ready и запуска очередей; deploy данные не переносит. Второй перезапуск ждёт готовности четырёх серверов. Затем Claude проверяет `team_status`: один релиз, единое хранилище, Grok подключён. Последующие выпуски требуют одного развёртывания.

Задания без ещё не полученного результата переносятся с отметкой «перенесено без результата». Повреждённые завершённые задания сохраняются в `state/quarantine/<номер>` со состоянием «ПЕРЕНОС: ПОВРЕЖДЁН» и не принимаются как голоса. Подробности — `state/migration.log`.

Метка готовности переноса не запрещает повторную сверку: новые основные серверы проверяют прежние источники при каждом запуске и каждые пять минут, пока источники существуют. Поздний окончательный результат заменяет незавершённый комплект, новые задания дозабираются, разные окончательные комплекты попадают в карантин. Это покрывает записи старых гостевых серверов Codex и Antigravity до их перезапуска. Ошибки, номера заданий и причины карантина показывает `team_status`.

## Что изменилось в версии 0.5.0

- Сводка стала короче: видны текущие работы, ближайшие шаги и сколько уже завершено. Подробности можно открыть отдельно.
- Строка нагрузки показывает, сколько работы получили Claude, Codex, Antigravity и Grok. Claude передаёт код, тексты и большие материалы помощникам.
- У работ появились понятные русские названия.
- Grok участвует в проверке замысла и результата. Его замечания учитываются, при этом обязательными проверяющими остаются Codex и Antigravity, решение принимает Claude.
- Установка сохраняет своё состояние. После перезапуска видно, чем она закончилась; второй выпуск не начинается, пока первый ещё запускает перезапуск.

Настройки Grok Bot меняет пользователь. Если для записи ответа понадобилось одобрение, Claude объяснит, какое одно правило добавить, и сохранит это замечание в журнале уроков.

Порядок установки, обновления правил помощников и отката описан в [служебном руководстве](docs/trio-v5-deploy.md).
