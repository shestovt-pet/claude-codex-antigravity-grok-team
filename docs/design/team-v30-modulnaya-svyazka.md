## 3. Устройство

### 3.1 Реестр участников

Хранилище: `state/members.json` — текущий снимок с номером версии `rev`; `state/members-log.jsonl` — отдельный журнал изменений (кто, когда, причина, дословная цитата пользователя, прежнее и новое значение); `state/members.json.last-good` — последний проверенный снимок. Запись — атомарно (временный файл + переименование) под файловой блокировкой `state/members.lock`, с проверкой `rev` (оптимистическая блокировка): пишут и `team_members`, и исполнитель автопаузы — оба только через `common/members-store.js`.
Повреждение: если `members.json` не читается — берётся `last-good` с предупреждением в team_status; если и он битый — новые запуски и принятие этапов останавливаются с понятной причиной. Встроенные значения `common/members-default.js` применяются только при первой инициализации (файла никогда не было), не при повреждении.

Запись участника:
```
id, family, title, specialization (текст для правил: «критика, логика, код» и т.п.)
adapter: codex-cli | agy-cli | dsh-headless | claude-print
adapter_params: путь, профиль, модели по задаче (например deepseek: read=deepseek-v4-flash, review=deepseek-v4-pro), способ авторизации
external: bool (anthropic-дирижёр — false; Codex/Antigravity/DeepSeek — true)
roles: {conductor, fallback_conductor, voter, writer, literary, receives, sends}
state: active | paused | removed
pause: {kind: manual|quota|outage|misconfig, scope: participant|model:<id>, since, until|null, next_probe}
```
Участник ≠ серверный процесс ≠ клиентское подключение: реестр описывает участников; `servers/<имя>` остаются как есть для совместимости; клиентские подключения (Claude Desktop, чаты Codex/Antigravity, DSH) описываются отдельно в `client-configs` и тоже строятся из реестра.

API `common/members.js`: `all()`, `active()`, `voters({excludeFamilies, external:true})`, `canSend(from,to)`, `canWrite(id)`, `adapterFor(id)`, `rev()`. Потребители из инвентаризации 076d7f54 плюс дополнения Codex: restart-hold.js, path-compat.js:50, state-migration.js:139 (старые хранилища jobs/codex-jobs остаются явной совместимостью), client-configs/client-rules (доставка правил новому клиенту, в т.ч. DSH).
Проверка-линтер: действующий состав не дублируется вне реестра (списки «кто участник/голосует/пишет»); распознавание моделей, исторические форматы и совместимость старых подключений законно содержат имена и линтером не ловятся. Grok в реестр не переносится.

Постоянное включение/исключение — `team_members add|remove` по слову пользователя (цитата в журнал) или решению дирижёра с этой цитатой. Новый участник на известном адаптере — без кода; новый тип адаптера — team_change.

### 3.2 Кворум

Обозначения: E — активные внешние голосующие семьи, кроме семей всех авторов этапа.
Приёмка этапа: нужно `min(2, |E|)` свежих «ПРИНЯТО» на одну редакцию от разных семей из E и ни одного открытого блокирующего. Если |E| = 0 — этап ждёт либо «выдан без принятия» решением пользователя. Исключение: если среди авторов есть anthropic (Claude), нужно 2 голоса; при |E| = 1 этап ждёт (сохраняется действующее «при авторе Claude замены нет», но теперь у Claude три внешних семьи).
Основание порога: решение пользователя 20.10 «2 из 3» (любые два внешних, кроме семьи автора) и действующее правило связки, по которому при авторе Codex работу принимает один Antigravity, когда другой внешней семьи нет (common.md, таблица «Кто принимает итог»). Один голос допускается только когда |E| = 1 и среди авторов нет anthropic; это фиксируется в отчёте этапа строкой «принято одной семьёй: другой допустимой нет». Смешанное авторство с anthropic и |E| = 1 — ожидание.
Примеры: автор Claude, все активны → любые 2 из 3; автор Codex → Gemini и DeepSeek, оба; авторы Codex+Antigravity → DeepSeek один; автор Claude, Codex на паузе → Gemini и DeepSeek.
Третьего голоса не ждём: как только набраны нужные «ПРИНЯТО», этап принимается; позже пришедший отказ — по действующему правилу запоздалого отказа.
team_change: «ПРИНЯТО» всех активных внешних голосующих семей, минимум 2; меньше двух — изменение ждёт.
Помощник Claude с чистой памятью на высоком риске — без изменений.

Открытые замечания живут в журнале замечаний этапа отдельно от состава: пауза, удаление, смена семьи их не снимают. Блокирующее замечание выключенного участника закрывается: (а) его же «ПРИНЯТО» после возвращения, или (б) «отклонено с причиной» дирижёром + пересмотр другой активной внешней семьёй из E, которая подтверждает отклонение (новый вид решения `reconsider_by_other`, с пометкой в отчёте). Возвращение участника не меняет уже принятые этапы; при чтении работы (team.js:131) принятые этапы проверяются по снимку состава на момент принятия.
Две записи одной семьи считаются одним голосом.
`reconsider_by_other` сохраняет все проверки нынешнего `reconsider` (stage-gate-v15.js:167): ссылка на исходный отказ, причина отклонения в тексте поручения, ответ позже отклонения, та же редакция и охват; плюс — проверяющий другой допустимой семьи из E. Ранее полученное обычное «ПРИНЯТО» пересмотром не считается.

### 3.3 Доказательство голоса

Голос засчитывается только из поручения, запущенного исполнителем моста, с неизменяемым снимком запуска: участник, адаптер, запрошенная модель, объявленная провайдером модель, семья (по модели, а не по адаптеру: Antigravity, запущенный на Claude, — anthropic, не google), уровень доказательства, rev реестра, work, stage, role=проверка, sha256 редакции. Несовпадение семьи → голос не засчитан. Для проверки обязателен новый сеанс без записи у всех адаптеров (сейчас — только у Codex, team-store.js:63); продолженный сеанс автора не может быть проверяющим.
Действующий запасной режим (rules/fallback.md, слово пользователя, чат-дирижёр) сохраняет свои доказательства без изменений.

### 3.4 Автопауза

Виды паузы и снятие:
- manual — только `team_members resume`; поздние ответы старых поручений её не снимают.
- quota — до времени сброса; если время неизвестно — проба раз в 60 мин дешёвым способом (источник квоты без вызова модели, где он есть; иначе минимальный вызов); квота одной модели Antigravity — пауза модели (`scope: model`), не участника, если другие модели доступны.
- outage — 3 подряд ошибки 5xx/таймаут/потеря процесса; проба раз в 15 мин тем же маршрутом.
- misconfig — ошибка авторизации/настройки: без автоснятия, уведомление пользователю.
Пауза адаптера claude-print не затрагивает основного дирижёра Claude.
Пишущее поручение участника, ушедшего в outage: по истечении срока молчания запускается остановка дерева процессов; замок области снимается только после подтверждённого завершения дерева (3.5), при неподтверждённой остановке — «нужно решение»; после снятия область помечается «возможна частичная запись — проверить» в team_status; читающие поручения просто помечаются.
Уведомление Windows и строка в team_status при каждой смене состояния.

### 3.5 Поручения от любого любому

Инструменты сервера team: `team_send(to, task, role, folder, write, model, …)`, `team_result(id, wait_sec≤40)`, `team_cancel(id)` (только свои поручения, поручения своей цепочки, или дирижёр/пользователь); codex_send/antigravity_send остаются совместимыми именами и идут тем же путём.
Исполнитель: отдельный долгоживущий процесс `most-runner` (один экземпляр по замку, автозапуск при входе в Windows, запускается и перезапускается deploy), не привязанный к stdio-серверам и Claude Desktop. MCP-серверы только ставят в очередь и читают.
Каждое поручение runner запускает через отдельный процесс-носитель `most-job-host`: носитель владеет дочерним процессом модели (дерево процессов в Windows Job Object), пишет поток вывода в постоянный журнал `state/jobs/<id>/stream.log`, разбирает результат тем же кодом, что сейчас серверы Codex/Antigravity (вынести разбор в общие модули), сам держит замок папки (файл замка с pid и временем запуска носителя) и сам освобождает его. Смерть runner носителей не убивает; новый runner находит живых носителей по их записям и подключается к журналу. Замок папки снимается только после подтверждённой остановки всего дерева (Job Object завершён); если остановка не подтверждена — папка остаётся занятой, состояние «нужно решение» в team_status, автоснятия по сроку молчания нет.
Перед каждым запуском — проверка restart-hold (team-v29).
Передача исполнения (кандидат Б): релиз Б несёт старым исполнителям Codex/Antigravity признак `executor_disabled` — они только ставят в очередь; deploy Б (1) прекращает приём новых запусков старыми серверами, (2) ждёт завершения идущих поручений старых серверов либо их явной остановки, (3) проверяет по записям готовности и списку процессов, что старых исполнителей не осталось (client-configs.js:137 — живые старые клиенты), (4) только затем включает runner для Codex/Antigravity. Не выполнен любой шаг — установка отказывает с причиной. Кандидат А исполнение не трогает.
Замок записи: единый для всех писателей (Codex, DeepSeek, Claude-print), совместимый с codex_folder; конфликт определяется по раскрытым реальным путям (realpath) для равных И вложенных областей в обе стороны. Дочернее пишущее поручение в области записи родителя — отказ до запуска (родитель не ждёт ребёнка в своей области). Если родитель только читает, конфликта областей нет, но право ребёнка на запись по-прежнему проверяется отдельно по правилу полномочий ниже (читающий отправитель без writer=true пишущего ребёнка запустить не может).

Цепочки и происхождение вызова: runner запускает каждое поручение с `MOST_JOB_ID` и `MOST_JOB_TOKEN` (HMAC номера поручения на секрете из state, действителен, пока поручение идёт; отзывается при завершении); client-configs передаёт оба значения MCP-процессам поручения (вместо одного MOST_JOB_ID, client-configs.js:53), это делают все адаптеры. Сервер team решает так: действительный токен → ребёнок (родитель из хранилища); MOST_JOB_ID без действительного токена, чужой или отозванный токен → отказ (одно идущее поручение может многократно отправлять и забирать результаты со своим токеном; каждая отправка дополнительно несёт одноразовый номер запроса, повтор уже обработанного номера → возвращается прежний ответ, а не новое поручение); нет ни того ни другого → проверка предков процесса: среди предков runner, носитель или процесс модели из активных поручений → отказ («происхождение не определено»); иначе предки — приложение-чат из перечня клиентских подключений (client-configs, строится из реестра; сейчас Claude Desktop, приложение Codex, Antigravity, DeepSeek Harness.exe) → новый корень; иначе отказ. Совместимые имена codex_send/antigravity_send проходят ту же проверку. Глубина ≤ 3; бюджет цепочки резервируется атомарно (по умолчанию 10 поручений на корень, отдельно — предел поручений Claude-print за 5 ч из реестра); цикл: пара отправитель→получатель внутри одного корня больше 2 раз подряд в обе стороны — отказ, плюс совпадение work/stage/sha256.
Полномочия: дочернее поручение не шире родителя; write=true только если у отправителя writer=true или отправитель — дирижёр, действующий запасной дирижёр (fallback_conductor при записанном слове пользователя) или чат пользователя; роль дирижёра не наследуется; отмена чужих — запрещена (кроме дирижёра, действующего запасного дирижёра и пользователя).

Поручения Claude (адаптер claude-print): `claude.exe -p` с JSON-выводом, отдельным `--mcp-config` (только сервер team), явным списком разрешённых инструментов по роли: совет/проверка — Read, Grep, Glob, WebSearch, WebFetch и team_send/team_result; текст/код с записью — плюс Edit, Write, Bash в папке поручения. Без сохранения сеанса — флагом установленной версии (проверить на 2.1.198). Получатель — отдельный сеанс Claude Code, не дирижёр; работу семьи anthropic не проверяет; тратит лимит Claude пользователя — отдельный счётчик в строке квот.

### 3.6 DeepSeek

Адаптер dsh-headless: `dsh --profile headless`, JSON-события, продолжение по session-id. Модели по задаче — deepseek-v4-flash (чтение, механика) и deepseek-v4-pro (проверка, код). Авторизация: сначала сохранённая авторизация DSH через настройку профиля (по документации headless её можно явно включить); ключ API — только если так не заработает, тогда ключ вводит пользователь сам. CLI dsh ставится в кандидате Б (npm), путь проверяется живьём.
Права как у Codex. Два режима запуска dsh-headless: «чтение» — профиль `most-read` с отключёнными инструментами записи и оболочки (только чтение файлов, поиск, веб); «запись» — профиль `most-write` с записью. Какие инструменты DSH реально отключаются настройкой профиля, проверяется живой пробой в кандидате Б (попытка записи из сеанса «чтение» должна получить отказ самого DSH). Пока такая проба не прошла, проверка DeepSeek идёт по снимку материала в отдельной временной папке, а его голос не засчитывается. Для режима «запись» граница — замок области и разрешённая папка как правило, а не техническая изоляция: пользователь принял риск для диска E (20.10), это записывается как граница доверия; изменения вне разрешённой папки обнаруживаются сравнением состояния диска E до/после только в пределах известных рабочих корней и попадают в отчёт. Имя модели (deepseek-flash или deepseek-v4-flash) сверяется с тем, что принимает установленный dsh.
DSH как клиент: подключение строится из client-configs (как у остальных клиентов), deploy и rollback сами переписывают пути в cordis.patch.yml на live\<хеш> — после отката DSH указывает на прежний релиз. Самодельные правки DeepSeek в рабочем дереве E:\most заменяются кандидатом А.

### 3.8 Notion для поручений Antigravity (дополнение 21.10)

Запрос пользователя 21.10 на вопрос «Нужен ли Notion поручениям Antigravity из моста?»: «Да».
Сейчас (поручение mvh8fxjt_c57b91) безоконный agy видит инструменты сервера notion, но (1) agy отклоняет вызов: нет правила разрешения; (2) мост сам отвергает MCP-вызовы кроме разрешённых: servers/antigravity/index.js:661 (текст поручения «Можно вызывать только…»), common/agy-tools.js:8,15–20, index.js:547 (вывод Codex a2262bf8).
Устройство:
- Права участника берутся из реестра: в записи antigravity поле `mcp_allow: ["notion/*"]` (список серверов/инструментов MCP, разрешённых поручениям участника). agy-tools.js пропускает вызовы call_mcp_tool только к серверам из mcp_allow; все остальные MCP (team, codex, antigravity, comfyui, pbta и любые другие) по-прежнему отвергаются. Текст поручения (index.js:661) перечисляет разрешённое из того же поля.
- Правило agy: `C:\Users\user\.gemini\antigravity-cli\settings.json` → permissions.allow `mcp(notion/*)` (синтаксис по документации agy: mcp(server/tool), mcp(server/*)); резервная копия перед правкой; deny/ask и прочие правила не трогать. Ставится установкой (deploy) из реестра и снимается откатом. Это глобальный файл: в обычном окне Antigravity вызовы Notion тоже пойдут без вопроса — для пользователя это допустимо (он сам просил Notion у Antigravity); изоляцию «только для моста» через --settings не вводим, пока её поддержка в agy 1.4.3 не подтверждена.
- Antigravity по-прежнему не пишет на диск; запись в Notion — по поручению, как у остальных участников.
- Входит в кандидат А как явное исключение из «поведение прежнее».
Проверки: тест — вызов notion/* пропускается фильтром, вызов team/* и codex/* отвергается, пустой mcp_allow — всё отвергается; живая проба после установки А — поручение Antigravity вызывает API-get-self и возвращает имя бота.

## 5. Опасные случаи

О1 подделка голоса меткой клиента или моделью другой семьи внутри Antigravity — голос только из снимка запуска 3.3, семья по модели.
О2 взаимные поручения без конца — глубина, атомарный бюджет, цикл по паре и по материалу, токен поручения.
О3 расход лимита Claude через claude-print — счётчик и предел в реестре.
О4 все внешние на паузе — этап ждёт, уведомление, никакой автоприёмки.
О5 два писателя в одной папке, родитель ждёт ребёнка в своей папке — единый замок, отказ.
О6 битый реестр — last-good, иначе остановка запусков; defaults только при первой инициализации.
О7 ложная автопауза — порог 3 подряд + проба тем же маршрутом; ручная пауза снимается только вручную.
О8 расширение прав через делегирование — дочернее не шире родителя, write только от писателя.
О9 смерть runner — восстановление без повторного запуска живых процессов.

## 6. Проверки

Именованные случаи: каждый из четырёх участников как чат и как поручение-сеанс отправляет каждому другому (12 направлений × 2) и забирает результат; отрицательные: читающий сеанс просит write=true у писателя — отказ; глубина 4 — отказ; цикл A↔B — отказ; бюджет — отказ; голос без снимка запуска или с семьёй не по модели — не засчитан; голос продолженного сеанса автора — не засчитан; битый members.json — last-good; ручная пауза + поздний ответ — пауза остаётся; квота одной модели Antigravity — пауза модели; родитель ждёт пишущего ребёнка в своей папке — отказ; закрытый Claude Desktop — поручения исполняются runner; фиктивный участник zzz — появляется в доступе, кворуме, сводке, правилах без правки кода.
Кворум: автор Claude — 2 из 3; автор Codex — Gemini+DeepSeek; авторы Codex+Antigravity — DeepSeek; автор Claude при паузе Codex — Gemini+DeepSeek; автор DeepSeek при паузе Codex — только Gemini (|E|=1, допустимо); блокирующее выключенного участника не исчезает.
Живые (после Б и В): Codex→DeepSeek, DeepSeek→Antigravity, Antigravity→Claude-print, Claude-print→Codex; искусственная пауза Codex на этапе автора Claude → принят голосами Gemini+DeepSeek.

## 7. Откат

В members.json хранится поле `phase` (A, B, C), записанное установкой; каждый релиз читает реестр через фильтр своей фазы: релиз А игнорирует receives/sends/адаптеры, которых у него нет (DeepSeek только читает); релиз Б принудительно считает DeepSeek voter=false и не применяет формулу 3.2 (действуют прежние ворота); базовый релиз members.json не читает вовсе. Поэтому откат В→Б, Б→А, А→база не оставляет действующих прав, которых у откаченного релиза нет; сам файл сохраняется для повторной установки.
Очереди и живые поручения при откате: новые запуски останавливаются; идущие поручения носителей доводятся до конца или явно останавливаются (с подтверждением остановки дерева); поручения адаптеров, которых нет в откаченном релизе, помечаются «потеряно при откате».
История принятия: у каждого принятого этапа хранится снимок решения (кто, семья, вид решения, версия ворот). Новые ворота (формула 3.2, reconsider_by_other) появляются только в кандидате В под новой версией правил; кандидаты А и Б ворот не меняют, но Б уже содержит неактивный код проверки версии ворот В, чтобы при чтении работы проверять снимок решения правилами той версии, которая его приняла.
Граница отката: инструмент rollback отказывает (с причиной и списком мешающих записей) в откате ниже релиза, способного прочитать существующие записи: при наличии этапов, принятых воротами В, — не ниже Б; при наличии записей реестра (members.json с phase) — не ниже А; до базы — только пока таких записей нет. Этапы, открытые на момент допустимого отката и опирающиеся на reconsider_by_other, получают «нужно пересмотреть». Проверка: откат с настоящей карточкой принятия воротами В — до базы отказ, до Б — после отката чтение работы кодом Б сохраняет принятие.
deploy/rollback переписывают подключения всех клиентов, включая DSH (cordis.patch.yml), на пути откаченного релиза; runner останавливается и запускается из откаченного релиза, если он там есть.
