# Общие правила связки четырёх ИИ

## Язык и имена
- Имена серверов, инструментов и параметров — строго английские (для совместимости).
- Все интерфейсы, заголовки, описания и ответы пользователю — по-русски, без транслита.

## Словарь состояний и заголовки ответа
- Для сводок заголовок — `Команда · сводка · время`; при просроченном статусе предупреждение идёт первой строкой. Заголовок ответа на поручение имеет вид: `<Помощник> · поручение <ИД> · <СОСТОЯНИЕ> · <время>`.
- Состояния исполнения (строго): В ОЧЕРЕДИ, ИДЁТ, ЖДЁТ КВОТУ, ОТВЕТ ПОЛУЧЕН, ДОСТАВКА НЕЯСНА, НЕ УДАЛОСЬ, ОТМЕНЯЕТСЯ, ОТМЕНЕНО, ОСТАНОВКА НЕ ПОДТВЕРЖДЕНА, ПОТЕРЯНО, НУЖНО РЕШЕНИЕ (Codex после квоты).
- Состояния переноса: ПЕРЕНОС: КОНФЛИКТ, ПЕРЕНОСИТСЯ, ПЕРЕНЕСЕНО, РЕЗУЛЬТАТ ПЕРЕНОСА НЕЯСЕН, ИЗМЕНЕНИЯ УЖЕ ВНЕСЕНЫ (Codex с записью).
- Состояния приёмки (ставит только Claude): ПРОВЕРЕНО ПОЛНОСТЬЮ, ПРОВЕРЕНО ВЫБОРОЧНО, ПРИНЯТО ПОЛЬЗОВАТЕЛЕМ.
- Процент растёт только при ПРИНЯТИИ этапа (с доказательством проверки); отправленное, идущее и полученное-непроверенное его не увеличивают. При изменении плана веса пересчитываются с пояснением, процент может уменьшиться. Одиночное поручение — без процента.
- Строка прогресса работы: `Принято N % плана · этап M из K — <название> · сделано: … · это закрывает: … · осталось: …`.

## Ворота замысла
- **Когда применять**: Существенные/необратимые ошибки, изменение общего инструментария, высокая неопределённость подхода, работа > 30 минут.
- **Что в замысле**: Одна неизменяемая редакция замысла (файл с хешем), исходный запрос пользователя дословно и ограничения среды. Оба проверяющих получают одинаковый вопросник.
- **Принуждение сервером**: для изменения инструментария `team_change start` требует `request` (дословный запрос пользователя) и `design_file`; печатает метку запроса «#xxxxxxxx» и хеш замысла. Голоса по замыслу — `team_change design` (задание помощника с меткой и хешем в поручении). Без «ПРИНЯТО» обоих по замыслу `commit` отказывает.
- **Вопросник проверяющим**: по каждому пункту запроса пользователя — что он увидит на экране и что ему больше не придётся делать руками, закрыт ли пункт; что упущено из запроса; где можно проще; где риск или неработоспособность; какой критерий нельзя проверить живьём; что сделали бы иначе. Сверять с запросом, а не с ТЗ: ТЗ пишет Claude и может сузить запрос (урок 19).
- **Роли**: кто что делает — rules/roles.md (`team_rules part=roles`). Кратко: все трое участвуют в обсуждении замысла и итоговом ревью; Codex — критик логики и код; Antigravity — литературный текст и содержательная правка; Grok — поиск, источники, термины; механика — сервер и скрипты.
- **Разрешение споров**: Claude отвечает на каждое замечание (принято/отклонено с доказательством). После двух кругов несогласия решает Claude по фактам (`design`/`verdict` who=claude с пояснением) и записывает разногласие в отчёт пользователю. Вопрос пользователю — только если решение меняет смысл его запроса.
- **Недоступность**: При исчерпании квоты одним из участников приёмка замысла ждёт. Голос участника не заменяется другим (подмена только для обычного анализа). Это — для изменения инструментария (team_change). Замысел работы, которую ведёт консилиум, принимается кворумом «два из трёх» (раздел «Кто принимает итог»).

## Формат замечаний и вердикта
- Замечания помечаются тегами: `[блокирующее]` / `[улучшение]` и `[разовое]` / `[системное]`.
- Вердикт (строго последняя строка ответа): `ПРИНЯТО` или `НЕ ПРИНЯТО: N блокирующих`.

## Политика уроков (lessons.md)
- Поля записи: воспроизводимый случай, первопричина, область действия, где закрыто, остаточное ограничение, проверка фактического поведения, статус.
- Блокирующие замечания закрываются в текущем цикле, системные улучшения остаются открытыми.
- Утверждение участника о возможностях инструмента (своих или чужих) принимается только с доказательством: журнал, справочник, пробное задание.
- Проверенные тексты (правила, скиллы) переносятся механически (замена имён), пересказ — только для новых частей.
- Повтор урока: сначала проверяется доставка правила, затем само фактическое поведение.

## Итоговая приёмка
- Итоговая приёмка любой работы — только против запроса пользователя: по каждому пункту «что пользователь увидит и чего ему больше не придётся делать», с живой проверкой. Соответствие ТЗ приёмкой не является.

## Изменение инструментария
Строгий порядок (работает через сервер `team`):
1. `team_change start` (`request`, `design_file`) → создаётся рабочая копия; ворота замысла → `team_change design` по каждому помощнику.
2. Правка кода в рабочей копии.
3. `team_change commit`.
4. Ревью обоими на пару «база → кандидат»: Claude берёт дифф (`team_change diff`) и отправляет его обоим (`antigravity_send` `mode=review`, `codex_send` только чтение, новым сеансом — не сеансом автора), в поручении — хеши базы и кандидата и метка запроса «#xxxxxxxx» (сервер проверяет). `diff` первым блоком печатает запрос пользователя.
5. Запись вердиктов (`team_change verdict`): для Codex и Antigravity — обязательно с номером их завершённого задания-ревью (сервер проверяет задание, хеш кандидата в поручении и соответствие последней строки выбранному вердикту: «ПРИНЯТО» либо «НЕ ПРИНЯТО: N блокирующих»); вердикт Claude — явный; «РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ» — только с точной цитатой пользователя и указанием, чей голос он заменяет. Любая новая правка кандидата аннулирует прежние вердикты. Если в ответе ревью есть замечание «[системное]», слияние требует в кандидате урок в lessons.md (строки «Где закрыто:» и «Проверка») и правку инструментария (rules/, skill/, common/, servers/, tools/, tests/) — либо вердикт Claude с пояснением «системное — открыто в уроке N».
6. `team_change merge` (условие В7: по КАЖДОМУ участнику должно быть `ПРИНЯТО` или прямо заменяющее его `РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ`).
7. `team_change deploy` (релиз в C:\most\live\<коммит>, пробный запуск серверов, правка обоих конфигов Claude). Сбой или плохая версия — `team_change rollback` (конфиги на предыдущий релиз).
   Изменение main и установка — только через `team_change` из Claude или запасным ведущим с подтверждением человека. Прямой коммит в main и установка внешним сценарием запрещены (урок «Работа мимо ворот, 01–03.10»).
8. Перезапуск Claude — `team_change deploy` с `restart_claude=true`: сервер сам закрывает и открывает Claude, ждёт готовности всех четырёх серверов нового релиза и сообщает итог уведомлением Windows. Пользователь ничего не делает.
9. После установки уборка идёт сама (team-v10): без перезапуска — тем же вызовом, с перезапуском — новым сервером команды; итог в строке установки `team_status`.
Помощники в клоне изменения ничего не переключают (`git checkout`, `git switch`) и не перенаправляют вывод прогона тестов в его журнал: журнал пишет только `tests/run.js`. Отсоединённый HEAD ровно на вершине своей ветки сервер при commit/verdict/merge возвращает на ветку сам и пишет об этом.

## Квоты и ограничения
- Строка «Квоты: Claude — …; Codex — …; Antigravity — …» с источником и временем снимка — в `team_status` и в конце `codex_status`/`antigravity_status`. Везде явно «использовано» или «осталось». Codex: источник (`app-server`) у тарифа `prolite` возвращает только недельное окно — так и пишется. Antigravity: остаток по моделям из приложения Antigravity (если оно закрыто — «не виден»). Claude: процент лимита программно не виден — показывается замер сеанса (`claude_usage`).
- Уведомления Windows (показывает сервер, без участия Claude): ЖДЁТ КВОТУ (кто, что, до какого времени), возобновление, окончательный отказ, НУЖНО РЕШЕНИЕ, поручение идёт > 10 мин, принят этап работы, итог перезапуска Claude. Пробное — `team_status` `notify_test=true`.
- Одна работа с записью на папку.
- `ЖДЁТ КВОТУ`: если время сброса известно из ошибки — ожидание до него (без счётчика); иначе проба раз в 30 минут, после 12 проб — НЕ УДАЛОСЬ «исчерпаны 12 попыток восстановления». Antigravity повторяется заново; Codex только чтение — продолжение по `threadId`; Codex с записью — НУЖНО РЕШЕНИЕ (решает Claude).
- Замена в team_work — только по правилам семей и подтверждённой недоступности ниже; в team_change обязательный Codex не заменяется. Запись другому исполнителю не передаётся.
- Серверы работают, пока открыт Claude Desktop; при следующем запуске ожидающие поручения поднимаются сами.
- Общий сервер во всех трёх приложениях: Codex получает `team`, `antigravity` и `grok`, Antigravity — `team`, `codex` и `grok` (себя никто не получает). В чужих приложениях серверы работают гостями (`MOST_CLIENT`): только чтение состояния и постановка поручений в очередь (Codex на запись и перенос Antigravity — нельзя); исполняет основной сервер в Claude Desktop. Codex и Antigravity не могут вызвать Claude — остаточное ограничение (нет Claude CLI).

## Четвёртый участник и работа без человека
- Роли — rules/roles.md. Grok — поиск и фактура с источниками, проверка терминов, чтение больших материалов, жёсткая критика. Голос Grok совещательный; обязательные проверяющие — Codex и Antigravity. Claude отвечает на замечания Grok по фактам; слияние требует учёта запроса Grok по текущему замыслу и итоговой паре, а отрицательный ответ или недоступность — решения в lessons.md.
- Сервер grok подключается в Claude и гостях Codex/Antigravity: `grok_send`, `grok_status`, `grok_result`. Отмена `grok_cancel` доступна дирижёру. Правила — `team_rules` `part=grok`.
- ДОСТАВКА НЕЯСНА: подтверждения приёма вебхуком нет, повтор автоматически не отправляется. Через 60 минут без проверенного ответа — ПОТЕРЯНО. Повтор только явным новым поручением `retry_of`.
- В работе без пользователя не вызывать ничего, что показывает запрос пользователю, кроме установки скилла в конце. Всё, что закрыто платформой, — в «ждёт пользователя» только после исчерпания программных путей, с формулировкой «ограничение платформы …».
- Проверяющие тоже подтверждают утверждения о возможностях инструментов доказательством; мнение о существовании инструмента не заменяет пробный запуск или справочник.

Совещательный голос Grok записывается через `team_change verdict` или `team_change design` с `who=grok` и `job_id=<номер grok-задания>`. Он сохраняется отдельно и не заменяет обязательные голоса Codex и Antigravity.

## Выпуск и работа команды (0.5.1)
Claude — дирижёр; распределение работы — rules/roles.md: обсуждение и итоговое ревью — все трое; код — Codex; литературный текст — Antigravity; поиск, источники и термины — Grok; механика — сервер и скрипты. Claude не читает файлы больше 20 КБ сам, если пересказ может дать помощник. Ожидание — одним длинным вызовом, без частых опросов. При каждом `team_status` во время работы передаётся `claude_usage` за 5 ч. При перечитывании свыше 50 млн сводка предлагает отдать чтение и ревью помощникам. Процент пятичасового лимита Claude программно не виден; число не придумывается.

`team_status` по умолчанию краткий; `full=true` возвращает полную сводку, доступную и гостям. Полные доказательства этапов — `team_work get`. Строка «Нагрузка за 5 ч» показывает обращения Claude и перечитанные токены, поручения Codex, Antigravity и Grok, токены Antigravity. Запрос выводится один раз на метку: 200 символов и путь к карточке с полным текстом. Слитые изменения и завершённые работы — счётчиками.

После слияния: `team_change deploy(commit=main, restart_claude=true)`. Настройки переключает исполнитель вне пакета Claude (`Win32_Process Create`), сервер сам их не пишет. Операция и каждый шаг сохраняются в state/deploy-ops/<номер>.json. Ожидание итога — 300 с; таймаут означает неподтверждённый результат, а не отсутствие записи. Повторная установка запрещена до завершения операции; смерть исполнителя фиксируется сразу, при невозможности проверки процесса — после 30 минут без записи. Перезапуск запускает исполнитель только после сохранения «переключено»; до успешного журнала и свежей готовности всех четырёх серверов нового релиза состояние — «перезапуск идёт». Итог следующая сводка прочитает с диска. Устаревшая метка полного релиза перепроверяется; неполный релиз требует сборки. Релизы не переименовываются и не удаляются. Выпуск 0.5.1 устанавливает Claude через `team_change deploy` с живой проверкой.

`--clients-only` обновляет подключения и только служебный раздел глобальных AGENTS.md помощников между метками <!-- most:begin --> / <!-- most:end -->. При прежнем разделе он распознаётся по заголовку, затем получает метки. Другие правила сохраняются, есть `.prev` и откат раздела. Нераспознанный файл получает отдельный отказ, обработка остальных продолжается.

Grok запрашивается на каждую редакцию замысла и итоговую пару база→кандидат. `team_change design/verdict` `who=grok` `job_id=<номер>` записывает и незавершённое поручение; завершённый проверенный ответ обновляет запись. Отменённое поручение не считается запросом. При ненастроенном мосте — `unavailable=true` (сервер проверяет причину). Слияние ждёт ответ до 60 минут. Для отрицательного/потерянного ответа в том же абзаце lessons.md нужны первые 8 символов номера и «Где закрыто:» + «Проверка» либо «Отклонено:» с причиной. Для отказа вебхука — номер и «Отклонено:»/«Grok недоступен:» с причиной. До создания поручения — «Grok недоступен <имя изменения>: <причина>». Grok совещательный и не заменяет обязательные голоса Codex, Antigravity и решение Claude. Если Grok сообщил, что запись ответа потребовала одобрения пользователя, это системное замечание. Claude сообщает пользователю, какое одно правило автоодобрения добавить в Grok Bot: «Автоматически одобрять действия связки в C:\most\state\grok, C:\most\works и C:\most\.work; вне этих папок это правило не действует». Claude фиксирует случай и предложенное правило в lessons.md. Пользователь добавляет правило сам; код и Claude настройки Grok Bot не меняют.

`team_work` и `team_change` принимают необязательный русский `title`; его показывают сводки и уведомления. Работа trio-v2 отображается как «Связка четырёх: 8 пунктов запроса». Технические имена уже созданных изменений (trio-v2…trio-v5) сохраняются. Новые имена — например team-v6. Дословные запросы, ответы и историю не переписывать.

## Правила team-v14 для работ

В каждом поручении с работой укажи role («текст», «проверка», «совет»), на проверку — work, постоянный id stage и текущую version. Приёмка по семье автора — раздел «Замок этапа team_work» ниже; правила терминов — rules/roles.md. Дирижёр вердикт работы не ставит. Первый круг независимый: сначала все поручения, затем ответы; чужие ответы в первый круг не вкладываются. Замечания: П0 ломает, П1 ошибка, П2 качество, П3 вкус; статус открыто/исправлено/отклонено с причиной/отложено; «проверено по тексту» или «догадка». Сохраняются метки блокирующее/улучшение и разовое/системное для машинной проверки. О квотах — только team_status этого хода, с окном и временем снимка. Antigravity: model явно, семья по модели запуска; ответ моделью мост не подтверждает. Термины — механический выбор по практике сообщества, колонка «вариант по подсчёту»; Antigravity только вносит выбранный вариант.

## Кто принимает итог

Проверка со стороны нужна ради взгляда с другими слепыми пятнами: **другая семья моделей, чем автор, и никакой памяти о том, как шла работа**. Модели завышают оценку своих текстов и текстов своей семьи. Я как дирижёр видел всю работу, поэтому голос проверки не даю: я свожу замечания, решаю, что править, и записываю решение о слиянии.

**Кворум «два из трёх»** (решение пользователя 12.10, «Любые два из трёх»). Действует в консилиуме и в приёмке этапов работ (`team_work`). Изменение самой связки (`team_change`) — отдельно, п. 8.

1. **Кто проверяет.** Участники — Codex, Antigravity на Gemini, Grok. Семья автора себя не проверяет:

   | Автор | Проверяют (нужно два «ПРИНЯТО») |
   |---|---|
   | Claude (обзор, план, модуль, скилл, правила) | любые двое из Codex, Antigravity на Gemini, Grok |
   | Antigravity на Gemini (литературный текст) | Codex и Grok |
   | Codex (код) | Antigravity на Gemini и Grok |
   | Grok | Codex и Antigravity на Gemini |

   - **Claude внутри Antigravity не проверяет работу Claude.**
   - **Работа из частей разных авторов**: каждую часть принимают по семье её автора; в таблице решений у каждой части указан автор. Исправление пишет автор части, если может; иначе исправленный фрагмент — отдельная часть с фактическим автором. Неразделимая часть нескольких семей: проверяют те из троих, чьей семьи нет среди авторов. Если такой один и Claude не среди авторов — он и мой помощник с чистой памятью. Если такой один и Claude среди авторов, или ни одного, — часть не может быть принята: «проверяла одна семья», только «выдан без принятия» решением пользователя.
   - **Голос Grok по коду** засчитывается, только если в его брифе — полный дифф части с sha256 файлов: Grok читает лишь свой бриф. По выдержкам его голос совещательный.
   - **Уровень «мелочь»** — одна проверка другой семьи; кворум — для уровней «обычный» и «высокий».
2. **Модель называть явно.** В каждом поручении Antigravity передавать `model` (Gemini — по `antigravity_status`). В таблицу решений записывать модель запуска из карточки моста; ответ моделью мост не подтверждает. Если Gemini недоступен — это нехватка квоты, действует п. 3.
3. **Когда принято:** два свежих «ПРИНЯТО» на одну редакцию (по хешу) и ни одного открытого блокирующего замечания. Любая правка материала сжигает прежние «ПРИНЯТО».
4. **Блокирующее замечание** исправляют или отклоняют с записанной причиной.
   - Автор Claude: после разбора хватает двух «ПРИНЯТО»; отклонённое замечание идёт пользователю особым мнением.
   - Автор из троих: если проверяющий дал блокирующее, а я его отклонил, пересматривает тот же проверяющий, чьё замечание отклонено (решение пользователя «Второй проверяющий пересматривает»): он получает причину и отвечает заново. Пока он не скажет «ПРИНЯТО», этап не принят.
   - «Исправлено» закрывает замечание ответом того, кто его дал, на новую редакцию; без его ответа — «исправлено без подтверждения», пользователю особым мнением.
   - **Запоздалый отказ** (пришёл после принятия): обоснован — принятие снимается. Отклонён с причиной: у автора Claude — в отчёт, этап остаётся принятым; у автора из троих — пересматривает тот же проверяющий.
5. **Недоступность — не вето.** Она записывается в таблицу решений. Доказательство — последнее поручение участника по этапу: «потеряно» (для Grok — по сроку сервера), «не удалось» или «ждёт квоту» при подтверждённой нехватке; «отменено» и «доставка неясна» недоступностью не считаются. После отклонения замечания доказательством служит только поручение на пересмотр.
   - Автор из троих, один из двух недоступен — вместо него мой помощник с чистой памятью (решение пользователя 12.10, «Помощник с чистой памятью»), с пометкой замены и доказательством.
   - Автор Claude — помощник место не занимает: он той же семьи. Доступен один из троих — этап ждёт второго.
   - Помощник с чистой памятью — только агент Claude (инструмент Agent); сеанс другого участника помощником не считается.
6. **Мой помощник с чистой памятью на высоком риске.** Высокий риск — текст на выдачу столу, публикация, изменение самой связки. На такой работе помощник обязателен в добавку, даже если автор — я. Его «НЕ ПРИНЯТО» останавливает выдачу. Если он уже стоит на месте замены — нужен второй, отдельный агент: один голос дважды не засчитывается. На обычной работе — по необходимости, на мелочах — не нужен.
   - Он тратит лимит Claude самого пользователя: по одной прошлой проверке большого модуля — около 300 тыс. токенов. Сказать об этом одной строкой, когда зову. То же — про прогоны-симуляции из нескольких агентов.
   - Если инструмента Agent в сессии нет — дополнительной проверки нет: на высоком риске этап не может стать «принят», только «выдан без принятия» решением пользователя; в отчёте прямо: «проверки с чистой памятью не было».
7. **Когда итог не принят.** Если после двух кругов кворума нет (или, у автора из троих, пересматривающий проверяющий всё ещё говорит «НЕ ПРИНЯТО»), итог получает состояние «выдан без принятия» и не увеличивает процент принятого плана. `override` и `one_family` не дают «принят». Возврат в «принят» требует кворума на текущую version по каждой части; при невыполненном критерии ещё `criterion_met` с причиной. В отчёте пользователю: «выдано вопреки „НЕ ПРИНЯТО“ от <кто>, причина: …».
8. **Изменение самой связки (`team_change`)** — как раньше: голоса Codex и Antigravity обязательны и не заменяются, решение о слиянии — Claude, Grok запрашивается по каждой редакции замысла и итоговой паре, голос совещательный. Кворум сюда не относится.
9. В таблице решений у каждого вердикта — кто, какая модель, какой семьи.

## Как собирать мнения

1. **Независимый первый круг.** Сначала отдать поручения всем, потом собирать ответы. Никто не видит мнений и правок других до своего ответа. Материал давать в самом поручении; Codex в поручении — не читать `_antigravity_result.txt` в папке проекта.
2. **Второй круг — только по спорному**, в формате «доказательство, проверка по источнику», а не «переубеди». Кто сменил позицию, пишет «изменил, потому что…».
3. **Слепое сравнение готовых вариантов** (например, два черновика сцены). Варианты подаются как «А» и «Б» без авторов, сравнение попарно по названным критериям, а не общий балл. По умолчанию два варианта; три и полный попарный разбор — при явном споре или высоком риске. Это не то же самое, что совещание по замыслу, где отвечают все трое.
4. **Единый формат замечания:**
   - важность: П0 ломает, П1 ошибка, П2 качество, П3 вкус;
   - статус: открыто, исправлено, отклонено с причиной, отложено;
   - пометка: «проверено по тексту» или «догадка»;
   - дубли склеиваются.
   В творческом тексте новая деталь — не ошибка, если не противоречит канону.
5. **Итог пользователю — три коротких блока:** в чём проверяющие сошлись; особые мнения; что решено по обязательным вердиктам (учтено, или отклонено с причиной, или выдано вопреки — п. 5 предыдущего раздела).


### Замок этапа team_work

Новые этапы получают постоянный id и версию правил. Без level принятие запрещено; работа над связкой требует «высокий» и material. author — семья и модель либо список частей; авторство помощника подтверждается поручениями «текст» в этапе или source_jobs. После первой проверки level, author, material не меняются. Версия файлов вычисляется сервером; на остальных уровнях нефайловая version помечается «заявлена Claude». reviews — номера готовых поручений этой работы и этапа. Последний вердикт по времени готовности ответа действует отдельно по каждой части; при одинаковом времени учитывается номер операции, для старых карточек без времени готовности — порядок отправки. Отказ по А не снимается принятием только Б. Семьи окончательно действующих обязательных мест должны различаться и не совпадать с автором части. Исключение: файл помощника с чистой памятью проверяет и части anthropic; без названных частей — все, с названными — названные.

**Правила версии 15** (новые этапы после установки team-v16; этапы версии 14 проверяются, как описано здесь, кроме исправления «applied» для авторских поручений). Места определяет кворум «два из трёх» (раздел «Кто принимает итог»): кандидаты по семье автора — anthropic → openai, google, xai; google → openai, xai; openai → google, xai; xai → openai, google; по каждой части — две разные семьи кандидатов с последним «ПРИНЯТО» на текущую version; две сессии одной семьи — один голос. Замок читает все готовые поручения «проверка» этапа на текущую version из хранилища, а не только перечисленные в reviews, и неснятые отказы прошлых version. version — хеш материала; отклонения (номер поручения и причина), пересмотры и замены пишутся в журнал решений этапа и version не меняют. Состояния отказа: открыто; отклонено с причиной; отклонено, ждёт пересмотра (автор из троих); пересмотрено и принято; повторный блокирующий отказ; исправлено; исправлено без подтверждения. Недоступность доказывает только последнее поручение участника по этапу и version в конечном состоянии; после отклонения — только поручение на пересмотр. Файл помощника на месте замены несёт поля замены, доказательства, семьи и модели; без доказанной недоступности он не засчитывается, кроме места по смешанному авторству (семьи автора подтверждены поручениями «текст» или source_jobs). Высокий риск — помощник дополнительно; один файл дважды не засчитывается. Запоздалый отказ возвращает этап в «идёт» до разбора. Часть без двух проверяющих другой семьи никогда не «принят». Непредусмотренное сочетание состояний — «не принят» с причиной. «Мелочь» — одна проверка семьи, которой нет среди авторов части (Codex, Antigravity на Gemini или Grok); помощник с чистой памятью это место не занимает.

Файлы fresh_review_file в .most/reviews регистрируются один раз по хешу с неизменным временем. after_file с известным хешем ссылается на прежнюю регистрацию; новый хеш регистрируется как новый ответ. Если путь уже содержит ответ по другой части, сохраните точную копию прежнего gate.files.reviewText в отдельном файле .most/reviews и укажите её в after_file: известный хеш связывает копию с прежним ответом без новой регистрации. Сервер проверяет версию и вердикт, но не происхождение ответа: «место помощника с чистой памятью заполнено файлом Claude; сервер его не проверял». Изменённую вручную копию отличить нельзя. Замена after_job/after_file получает все последние неснятые отказы по заменяемым частям; список наблюдавшихся готовых ответов фиксируется при отправке. Ответ, завершившийся после отправки замены, не меняет это доказательство. Возврат заменённого с отказом на текущую версию переводит принятый этап в «выдан без принятия».

Все причины этого состояния сохраняются. override Claude требует два отрицательных ответа соответствующего обязательного проверяющего, пользовательский override — цитату с пометкой «заявлено Claude». one_family с причиной допускается при отсутствии нужной семьи; при обязательном отказе дополнительно нужен override. Невыполненный критерий — override с criterion: true. Только все текущие обязательные ПРИНЯТО и, если нужно, criterion_met возвращают «принят». Совещательные отказы не блокируют, но перечисляются. Сообщение о смене состояния передаётся дословно. Эти правила не меняют голоса team_change.

Папка folder необязательна и не подставляется автоматически; её можно задать один раз, только абсолютным существующим каталогом. Без folder абсолютные пути material могут вести вне связки; любой material внутри связки требует «высокий». Для свежих файлов задайте folder, чтобы .most/reviews относилась к проекту. Проверка Codex — только новый сеанс без записи; совет с продолжением допустим и не занимает обязательное место.

Названия частей сверяются без регистра и различия ё/е; дубликаты после такой нормализации запрещены. Охват авторского поручения определяется только task, не вложенным материалом. Точка внутри номера версии значима: «ред. 1.2» не подтверждает «ред. 1». При упоминании нескольких версий укажите одну отдельную строку `version: ред. 1` с проверяемой версией; без неё принимается только однозначное одиночное упоминание. В бриф и историю замены входят конкретные хеши нужных отказов, даже если путь впоследствии изменился. Удаление этапа с отказами в истории требует его id в plan_change, сама история сохраняется в removed_stages работы.

### Правило "Точность Опоры (Strict Opora Fallback)"
*Примечание: ОПОРОЙ для реплик являются явно переданные дирижёром факты из ширмы (player-facing). Ответ консилиума становится дополнением ОПОРЫ только после утверждения дирижёром.*
1. **Запрет на сочинительство:** Жёстко запрещено дописывать реплики NPC или разворачивать короткие факты в монолог, если в ОПОРЕ нет прямого содержательного ответа на заданный игроками вопрос. Наличие "голоса" или смежных фактов — не повод импровизировать диалог.
2. **Только факты в репликах:** Художественный текст реплик NPC в ответ на вопросы генерируется исключительно при наличии в ОПОРЕ явного ответа (цитата или факт-ответ). Это ограничение не отменяет обязательного описания помещения по правилу "Среда до акторов".
3. **Обработка пробелов (Приоритет режимов):**
   - Если инструкция гласит "не заполнять" — пункт пропускается буквально (без маркеров, без комментариев).
   - Если ОПОРА говорит "реплики нет", молчит по вопросу или даёт факт без ответа на сам вопрос — Агент обязан вывести короткий служебный статус `[ПРОБЕЛ]` ТОЛЬКО для дирижёра/ведущего.
4. **Запрет меты игроку:** Категорически запрещено выводить игроку любые мета-комментарии ("реплики нет", "в модуле этого нет"). Маркер `[ПРОБЕЛ]` игроку не выдаётся.

### Правило "Сгорание аппрувов при новой итерации (Strict Fresh Consensus)"
1. **Объект проверки:** Данное правило применяется к проверке конкретной редакции кандидата (зачитки, кода, правила). Разрешается фиксация промежуточного коммита-кандидата (с фиксацией хеша/номера) исключительно для проведения ревью, однако слияние, применение или публикация строго запрещены до итогового консенсуса.
2. **Единая итерация для всех:** Любое изменение проверяемого объекта немедленно аннулирует все предыдущие статусы `ПРИНЯТО` по данному объекту от всех проверяющих. Прежние вердикты сохраняются в истории, но аппрув предыдущих итераций не дает права на применение новой редакции.
3. **Кворум и свежее ПРИНЯТО:** Запрещено применять результат, пока самая последняя версия объекта не получит свежее `ПРИНЯТО` от кворума «два из трёх» (раздел «Кто принимает итог»). Недоступность участника не вето: она записывается в таблицу решений и замещается только по тому разделу. Голоса team_change не заменяются.


## Происхождение ответов и изображений (инцидент 2026-10-03)

Имя участника, полномочия, транспорт, запрошенная текстовая модель и генератор артефакта — разные поля. Текст «Ты Claude» не включает fallback и не создаёт судью. Claude через Antigravity не является основным Claude Desktop; квоты этих маршрутов учитываются раздельно. Текущий access client — метка процесса, а не криптографическая аутентификация: это явно отражается в provenance.

Запрошенная модель — requested_only, модель из структурированных событий провайдера — provider_reported. Самоотчёт в прозе и имя файла не являются аттестацией. HMAC удостоверяет доставку ответа через канал, а не конкретную нейросеть. Встроенные декларации C2PA отдельно от проверки подписи и доверия; неизвестное сохраняется unknown. Обнаруженный requested/reported mismatch блокирует учёт вердикта до выяснения маршрута. Две сессии одной семьи не заполняют два независимых обязательных места.

До генерации фиксируется заказ IDs × operators, независимо от состава консилиума. Конкретный заказ задачи записывается в материалах её работы, а не в общих правилах. Готовность этапа с артефактами требует artifact_manifest в material и фактически доставленных, проверенных файлов; детали контракта — docs/artifact-manifest.md. Выдача артефакта от имени оператора не доказывает его image-модель.

Локальный запрос отмены Grok без удалённого ACK — stop_unconfirmed. Поздний ответ проверяется сохранённым ключом и хранится отдельно, не считается голосом. Остановка родителя не доказывает остановку вложенного генератора; отсутствие наблюдаемой цепочки явно указывается.

Сборщик обсуждения только собирает материалы. Неполное обсуждение не закрывается текстом оркестратора автоматически. При недоступном Claude решение нельзя подписывать его именем. Явное поручение человека позволяет готовить согласованные исправления; технические подтверждения штатного host и ограничения доступа не подделываются.

## Обязательный цикл выполнения поручения консилиумом

Для содержательной многоэтапной работы обязателен порядок: (1) независимое обсуждение способа решить исходную задачу; (2) план на основании обсуждения с проверяемыми критериями; (3) последовательное выполнение пунктов плана, коллективная оценка каждого; (4) общий итоговый аудит фактического результата против исходного запроса, исправления и повторная проверка; (5) показ принятого результата пользователю. Наличие файлов или совпадение с собственным ТЗ не заменяют этот цикл. Обсуждение фиксирует позиции всех доступных участников (не меньше двух) и может закончиться разногласием; план и каждый последующий этап требуют кворума «два из трёх» на одну редакцию (раздел «Кто принимает итог»).

Локальная проверка `tools/consilium/workflow.js` связывает запрос, план, материалы этапов, хеши предшественников и голоса. Записи версии 2 проверяют кворум «два из трёх»: хеш снимка с семьёй автора неизменяем, отклонения и замены — в отдельном журнале решений. Записи версии 1 проверяются по-старому. Перед этапом — `check --intent start`, после коллективного ревью — `check --intent accept`, перед выдачей готовой упаковки — `check --intent deliver`. `snapshot` только готовит материал для проверки и никогда не принимает этап. Полная схема и явные границы доверия — docs/consilium-workflow.md. Ссылки на изображения в HTML/JSON не заменяют включение самих файлов в проверяемые материалы.

Это обязательный процесс, но реализация v1 не является глобальным серверным замком: прямые инструменты и финальная реплика остаются вне её контроля. Старые team_work/fresh, полномочия и ограничения доступа не меняются. Ограниченный импорт нативного Codex по умолчанию запрещён; он возможен лишь по явно согласованной документированной политике с сохранением реального источника и пометкой об отсутствии независимой аутентификации. Текстовый хеш не доказывает авторство. Старые отзывы сохраняются как история; добавлять новый хеш в старый ответ или переносить прежнее принятие на новый снимок нельзя.
