# Сценарий: мост сам ведёт многоходовый прогон

Обычно поручения мосту шлёт чат (Claude и др.): один вызов — одно поручение, ответ приходит назад в чат, чат решает, что
слать дальше. Для слепых симуляций и других многоходовых прогонов это дорого: чат руками шлёт каждое поручение и опрашивает
результат, а каждое поручение — новый запуск без памяти, поэтому участник каждый ход перечитывает весь свой материал.

**Сценарий** переносит сам цикл в мост. Чат один раз запускает сценарий — дальше мост сам шлёт поручения, ждёт ответы и по
ответу «крючка» решает, что слать дальше. Чат в цикле не участвует.

## Из чего состоит сценарий

1. **Файл сценария** — JSON. В нём лежат произвольные настройки игры (их читает крючок) и ссылка на крючок:
   ```json
   {
     "id": "моя-симуляция",
     "title": "Стол на четверых",
     "turns": 3,
     "parallel": 4,
     "hook": { "interp": "C:\\Program Files\\nodejs\\node.exe", "script": "E:\\...\\table-hook.js" }
   }
   ```
   `interp` и `script` — абсолютные пути интерпретатора (node или python) и скрипта крючка. Папка файла сценария становится
   рабочей папкой крючка (cwd).

2. **Крючок (hook)** — внешняя команда владельца (node/python). Мост не знает правил игры — их знает крючок. На каждом шаге
   мост запускает крючок, подаёт ему JSON на stdin и читает JSON со stdout.

## Протокол крючка (одна команда на шаг)

Мост → крючку:
```json
{ "event": "start" | "results",
  "scenario": { ...файл сценария... },
  "state": <то, что крючок вернул в прошлый раз, или null на старте>,
  "results": [ { "key": "gm", "member": "deepseek", "status": "done",
                 "text": "...", "resultFile": "...", "error": null,
                 "seconds": 7.2, "chars_in": 231000, "chars_out": 1800 } ] }
```

Крючок → мосту:
```json
{ "state": <любое, вернётся на следующем шаге>,
  "send": [
    { "key": "gm",
      "member": "deepseek",            // или "members": ["deepseek","kimi","codex"] — порядок предпочтения
      "level": "strong",               // fast | normal | strong
      "role": "совет",
      "task": "Веди ход 2. ...",
      "files": ["C:\\...\\материал.txt"], // вложения: мост читает и вкладывает в поручение, участнику файлы открывать не нужно
      "session": "gm",                  // имя сеанса — мост сам ведёт continue_id по имени (память между ходами)
      "fresh": false,                   // true — начать сеанс заново
      "memory_file": "C:\\...\\сводка.txt", // если сеанс начинается заново — вложить этот файл как «память»
      "timeout_sec": 600 },
    { "key": "p1", "members": ["kimi","codex"], "session": "p1", "level": "fast", "task": "Ты игрок 1..." }
  ],
  "done": false,                        // true — сценарий завершён
  "note": "ход 2: ведущий" }            // короткая строка для сводки
```

- Все поручения из `send` уходят **параллельно**. Когда все завершились (done/отказ/сбой) — мост снова вызывает крючок с
  `event: "results"` и собранными ответами.
- Поручения сценария идут **тем же путём, что обычный `*_send`** (те же проверки, замки, профили, сеансы, вложения, учёт
  объёма и отметка лимита) — для всех участников (codex, deepseek, kimi, antigravity, claude). В карточке такого поручения
  стоят `scenario`, `scenarioKey`, `scenarioBy` (кто запустил), а `from` — клиент запустившего чата.
- **Сеансы**: мост хранит по имени сеанса последний номер поручения и подставляет `continue_id` — участник помнит прошлые
  ходы. `fresh: true` начинает новый сеанс; если у участника продолжение недоступно, память эмулируется вложением `memory_file`.
  **`memory_file` должен существовать** (мост вкладывает его целиком при рестарте сеанса); несуществующий файл просто
  пропускается. Кто помнит сеанс по-настоящему — ниже.
- **Обход по лимиту**: при `members: [...]` мост берёт первого, у кого нет действующей отметки «лимит исчерпан» и кто не на
  паузе; при отказе поручения по квоте/сбою — автоматически следующего из списка тем же ключом (сеанс начинается заново).
- **Вложения только нового**: вкладывайте постоянный материал (мир, правила) один раз на первом ходу сеанса; дальше — только
  новые события. Память несёт сам сеанс.

## Как запустить одной командой

Из доказанного чата любого участника связки:
```
team_scenario action=start scenario_file="E:\\...\\scenario.json"
```
Ответ назовёт риск («мост будет запускать команду <node> <script> на каждом шаге»), номер сценария и папку состояния.
Дальше мост ведёт цикл сам. Смотреть ход: `team_scenario action=status id=<id>` или `action=list`. Остановить —
`action=stop`, продолжить — `action=resume`. Незавершённые сценарии переживают перезапуск сервера и поднимаются сами.

## Образец крючка

`table-hook.js` — рабочий пример «стол: ведущий и игроки» (общий, без правил конкретной игры). Число игроков и раскладка
участников задаются в файле сценария (`players`, `gm_members`, `player_members`, `turns`, `summary_every`, необязательные
`secret` и `material`). Он:
- ведёт журнал (`work/журнал.jsonl`) и реплики в папке сценария;
- шлёт ведущему (level strong, сеанс `gm`): постоянный материал вкладывает **только на первом ходу сеанса**, дальше — только
  новые ходы игроков; ограничивает длину хода подсказкой;
- затем игрокам параллельно (level fast, свои сеансы) — каждому только нарратив ведущего (что ему положено слышать);
  накапливает «память игрока» в `work/память-<key>.txt` (чтобы при рестарте сеанса было чем эмулировать память);
- каждые N ходов берёт сжатую сводку как «память» и начинает сеанс ведущего заново (защита от переполнения контекста);
- если задан `secret`, кладёт его в материал первого хода и просит повторить по памяти в ходах 2+ — так видно, держится ли
  память сеанса.

## Что показал живой прогон (раскладка: ведущий [kimi, deepseek, codex] strong; игроки [deepseek, kimi, codex] fast)

Стол на 3 хода, материал ~1,5 КБ, секретное слово в первом ходу. По памяти сеанса (повтор секрета в ходах 2–3):

| участник | роль | память сеанса |
|----------|------|---------------|
| **kimi** (kimi-code) | ведущий | **да** — через `continue_id` → `--session` (секрет повторён в ходах 2–3) |
| **deepseek** (dsh flash) | игрок | **да** — через `continue_id` → `--session-id` (секрет повторён в ходах 2–3) |
| **codex** (gpt) | запас | **да** — через `continue_id` → threadId (проверено отдельной пробой) |
| **antigravity** (agy) | — | **да** (с cache-622) — через `continue_id` → `agy --conversation <id>`; id разговора мост берёт из поля `conversation_id` потока agy. Живая проба 23.11.2026 на agy 1.5.15: второй ход вспомнил слово из первого |
| **claude** | — | продолжение CLI не поддержано — в сценарии **эмуляция** вложением `memory_file` |

Объём входа всего стола (9 поручений): **сценарий ~11 КБ** против «как сейчас» (полный материал каждый ход, без сеансов) —
кратно больше (цифры — в отчёте). Ход стола сценарием — около 70 с на этой раскладке.

## Состояние на диске

`state\scenarios\<id>\`: `scenario.json` (копия), `state.json` (текущее состояние цикла), `steps.jsonl` (журнал шагов — время,
поручения, секунды и объёмы в знаках на каждом шаге). Это ведёт мост; свои файлы крючок держит отдельно.
